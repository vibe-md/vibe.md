You write documentation for vibe.md. Many readers are "vibe coders": people who build
with AI agents and may be new to Git and to the command line. Write for them.

## Style

- Match the tone of the existing docs: plain language, short sentences, active voice, and
  concrete commands and examples. Explain a term the first time it appears. Avoid jargon,
  hype, and filler.
- Before writing, read the surrounding document and one or two neighbouring files, and
  follow their structure, heading style, and table formats.
- Keep edits as small as the task needs. Don't restyle text you weren't asked to touch.

## Facts must match the repository

- Check every claim against the source before you write it: skill names and counts
  (`skills/`), installer flags (`scripts/install.sh --help` text in the script), agent
  directories, categories (`scripts/categories.py`), catalog fields
  (`scripts/build-packages.py`), and the publication process (`docs/MAINTAINERS.md`,
  `.github/workflows/`).
- Prefer linking to the source of truth over copying it. In particular, link to the
  generated `skills/README.md` index instead of listing every skill.
- If the docs and the code disagree and you can't tell which is right, don't guess. Report the conflict.
- Follow the SKILL.md format rules in `CONTRIBUTING.md` (frontmatter fields, description
  length and content, required structure) when you edit skill text.

## Hard rules

- **Never edit `skills/README.md` between the `skills-index` markers.** That section is generated by `scripts/update-skills-readme.py`. Change the source SKILL.md or package README instead.
- **Keep these headings exactly as written**, because the website reads them: `## When to Use` and `## Examples` in SKILL.md files, and `## Related skills` in package READMEs. Don't rename them, change their level, or translate them.
- **Don't change behaviour.** Don't edit `scripts/`, `.github/`, `tests/`, or code in a skill's `scripts/`, and don't change what a skill's instructions tell an agent to do. Wording that clarifies is fine; wording that changes the steps, safety confirmations, or scope is not. If a docs fix needs a behaviour change, say so and stop.
- Don't touch `name` in frontmatter, links that tools depend on, or the `skills-index` markers.
- Never add secrets, personal data, or private URLs.

## When you finish

List the files you changed and give a one-line reason for each. Note any facts you
couldn't verify, and say whether the change should be run past
`python3 scripts/validate-skills.py` (required for any SKILL.md or package README edit).
