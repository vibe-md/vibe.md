# Skills

This directory is the canonical home of vibe.md skills and skill groups:

```text
skills/
├── _shared/
│   └── vibe/SKILL.md    # general router, included in every installation
├── gitly/
│   ├── README.md
│   ├── gitly-status/SKILL.md
│   └── gitly-save/SKILL.md
└── <skill-name>/        # standalone skills remain supported
    ├── SKILL.md        # required: YAML frontmatter + instructions
    ├── scripts/        # optional: helper scripts the agent may run
    ├── references/     # optional: extra documentation loaded on demand
    └── assets/         # optional: templates, examples, data files
```

Gitly contains independently usable skills. Install the group with:

```bash
bash scripts/install.sh --group gitly --agent codex --project /path/to/project
```

This installs the `vibe` router and the `gitly-*` directories directly into
`.agents/skills/`. Each workflow has its own `SKILL.md`; the contract, license, and documentation
are shared once in `.agents/skills/gitly/`, including single-workflow installs.
Use `--skill gitly-status` for just one workflow plus the router. Replace `codex`
with your agent's name to use its discovery directory.

The router uses the installed skill catalog and each skill's description, so
future groups work without editing a central routing table. Project-level
`AGENTS.md` files are not created or changed. See [Gitly](gitly/README.md) for usage.

### [deploy](deploy/)

Take a site from "works on my computer" to a checked public web address, in plain language and with your approval at every step that matters.

- [deploy-frontend-check](deploy/deploy-frontend-check/SKILL.md) — Read-only check (edits no project files) of whether a website project is ready to go online. Detects the framework and package manager, runs the project's own build locally, finds the output folder and the environment variable names the code uses, and flags secrets in public variables, file-name case mismatches, unsaved or unpushed work, and backend or database parts that are out of scope. Ends with a plain ready or not-ready report. Use before a first deploy, or when the user asks "is my site ready to go online?", "can I deploy this?", "will this work online?", "האתר מוכן לעלות לאוויר?", or "תבדוק אם אפשר להעלות את האתר". Not for actually deploying (use deploy-frontend-launch), not for a build that already failed on the host (use deploy-frontend-fix), not for backend servers or databases, and not for Docker or VPS hosting, which this package does not cover.
- [deploy-frontend-choose](deploy/deploy-frontend-choose/SKILL.md) — Helps pick a hosting service for a website (Vercel, Netlify, Cloudflare Pages, or GitHub Pages) and explains why. Read-only. Looks at the framework, whether the site is static or needs server code, the free plan's current limits and rules (read live, with the date), custom domain plans, commercial use, and accounts the user already has, then ends with one recommendation, the reason, and a runner-up. Use when the user asks "where should I host my site?", "Vercel or Netlify?", "which host is free for my project?", "can I put this on GitHub Pages?", "איפה כדאי לי לארח את האתר?", or "מה עדיף, Vercel או Netlify?". Not for deploying (use deploy-frontend-launch), not for backend servers or databases, and not for Docker or VPS hosting.
- [deploy-frontend-domain](deploy/deploy-frontend-domain/SKILL.md) — Connects a custom domain (your own web address, such as my-site.com) to a website that is already online. Explains DNS records in plain words, checks the domain's current DNS before any change, adds the domain on the host, guides the user through the exact records the host shows (www versus the bare domain), warns about email (MX) records and costs, waits for DNS to spread, checks HTTPS, and verifies the address works. Asks before every DNS or host change and never buys a domain. Use when the user says "connect my domain", "use my own domain", "point my GoDaddy domain to Vercel", "my domain shows an error", "תחבר לי את הדומיין", or "איך שמים דומיין משלי על האתר?". Not for a first deploy (use deploy-frontend-launch), not for email hosting setup, and not for backend servers.
- [deploy-frontend-env](deploy/deploy-frontend-env/SKILL.md) — Sets up a website's environment variables (the named settings it reads, such as a service's address or a key) on its hosting service safely. Explains public versus secret, finds the names the site needs (names only, never values), flags secrets in public variables, and has the user enter each value in the host's dashboard or their own terminal for the right environments (production and preview), then checks the names and redeploys so build-time values take effect. Asks before every change. Use when the user says "add my API key to Vercel", "set environment variables", "my site can't connect to Supabase online", "where do I put my .env on Netlify?", "תגדיר לי משתני סביבה", or "האתר לא מתחבר ל-Supabase אחרי ההעלאה". Not for writing code, not for a first deploy (use deploy-frontend-launch), and not for backend servers.
- [deploy-frontend-fix](deploy/deploy-frontend-fix/SKILL.md) — Diagnoses a website build or deploy that failed on the hosting service, or a live site that is broken after a deploy. Reads the host's build logs (summarised, never copying secret values), matches the error to the common causes (Node.js version, missing environment variables, file names that differ only in capital letters, wrong build command or output folder, single-page app routes that give 404, missing base path, dependencies), reproduces it locally when it can, proposes the smallest fix, and asks before editing anything. Then redeploys with the user's yes and verifies the live site. Use when the user says "my deploy failed", "the build fails on Vercel", "my site shows 404 online", "blank page after deploy", "הבילד נכשל ב-Netlify", or "האתר מציג דף ריק אחרי ההעלאה". Not for a readiness check before the first deploy (use deploy-frontend-check), not for backend servers or databases, and not for Docker or VPS hosting.
- [deploy-frontend-launch](deploy/deploy-frontend-launch/SKILL.md) — Puts a website online for the first time and checks the live address before saying it is done. Runs deploy-frontend-check first, confirms the hosting platform (Vercel, Netlify, Cloudflare Pages, or GitHub Pages), helps the user log in safely, connects the GitHub repository or uses the platform's command-line tool, sets environment variables by name, asks before going public, deploys, verifies the live URL and its main pages, and explains how to update the site next time. Use when the user says "put my site online", "deploy my site", "publish my app", "give me a link I can share", "תעלה לי את האתר לאוויר", or "תפרסם את האתר". Not for checking readiness only (use deploy-frontend-check), not for updating a site that is already online (use deploy-frontend-update), not for backend servers or databases, not for custom domains on their own, and not for Docker or VPS hosting, which this package does not cover.
- [deploy-frontend-rollback](deploy/deploy-frontend-rollback/SKILL.md) — Undoes a bad deploy of a website by switching the live site back to the last version that worked, then checks the live address. Finds the earlier working deployment on the host, explains what will change, and with the user's yes promotes or restores it using the host's own rollback (Vercel, Netlify, or Cloudflare Pages) or by re-running or reverting through Git (GitHub Pages, or any Git-connected site), and says how new pushes behave afterwards. Use when the user says "my site broke after the last update", "put the previous version of my site back online", "undo the deploy", "roll back my site", "תחזיר את האתר לגרסה הקודמת", or "האתר נשבר אחרי העדכון, תבטל". Not for finding the cause of a failure (use deploy-frontend-fix afterwards), not for restoring code files on the computer (use gitly-restore), and not for backend servers or databases.
- [deploy-frontend-update](deploy/deploy-frontend-update/SKILL.md) — Ships changes to a website that is already online, safely. Checks the change builds, saves and pushes it (Git-connected hosts) or deploys it with the host's tool, uses a preview address to check the change first where the host offers one, asks before publishing to production, and checks the live site after every deploy. Explains preview versus production in plain words. Use when the user says "update my live site", "publish my changes", "push this to production", "I changed the homepage, put it online", "תעדכן את האתר באוויר", or "תעלה את השינויים לאתר". Not for the first deploy (use deploy-frontend-launch), not for undoing a bad deploy (use deploy-frontend-rollback), not for a failed build (use deploy-frontend-fix), and not for backend servers or databases.

### [security](security/)

Use when reviewing an application's image, document, receipt, invoice, scanned email, or attachment-processing pipeline for indirect visual prompt injection. Not for text-only prompt injection or general AI agent security (use security-agent-guard), image privacy and metadata handling (use security-media-privacy), or standalone phishing, malware, and suspicious-email triage.

## Adding a skill

1. Create `skills/<skill-name>/SKILL.md` or `skills/<group>/<skill-name>/SKILL.md`. The leaf directory must match `name`; names must be unique across the collection.
2. Use lowercase kebab-case for the name, for example `git-workflow`.
3. Write a `description` that says what the skill does **and** when an agent should use it.
4. Use local resource links or `../filename` for top-level group Markdown documents and `LICENSE`. Installation includes shared documents automatically. Set `metadata.collection: vibe.md` and `metadata.group: <group>` for routing.
5. Validate your work:

   ```bash
   python3 scripts/validate-skills.py
   ```

6. Open a Pull Request. CI discovers and validates the new skill automatically.

A regular contribution stays inside its skill or group directory. You never need
to edit the router, installer, validator, or CI to add a group. `_shared/` is
reserved for common skills automatically included in every installation.

See [CONTRIBUTING.md](../CONTRIBUTING.md) for the complete format, a full example, and the review checklist.
